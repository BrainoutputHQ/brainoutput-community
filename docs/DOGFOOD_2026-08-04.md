# Dogfood run — server-backed OpenCode runtime, full product loop — 2026-08-04

Verification mission. Goal: run a real project through the whole CE loop (create project → plan
→ validate → materialize → launch a CODING task) against a **live** CE web server started with
`BO_CE_OPENCODE_SERVER=1`, using the GB10 gateway model (`brainoutput-local/coder`,
`http://192.168.1.14:9000/v1/chat/completions`), and report exactly what breaks. Finding breakage
was the deliverable. This report is blunt on purpose.

Driver scripts (the only files added, per the mission's rule — no product code was modified by
this session; see "A collision I did not cause" below for one exception that was found and
reverted):

- `tools/oc-dogfood.mjs` — drives the real HTTP API end to end: starts the CE server in an isolated
  `BO_CE_DATA` dir on a random port, onboards a company, connects the GB10 model, assigns capability
  slots, creates a project, plans/validates/materializes a task, launches it, subscribes to the live
  SSE relay, polls to completion, and asserts real files on disk.
- `tools/oc-server-direct-probe.mjs` — a supplementary probe that calls `opencode-server.mjs`'s own
  `runOpenCodeServer()` directly (still the real REST runtime, still the real GB10 model) to isolate
  whether a defect found in the HTTP loop is unique to the web-server.mjs wiring or lives deeper.
- `tools/oc-reviewer-only-probe.mjs` — isolates the reviewer stage using the exact evidence
  (diff + test output) a real run produced, to measure the reviewer call's own behavior/timing
  independent of a full coding run.

All three ran against the real GB10 gateway (verified reachable, HTTP 200 on a raw
`/v1/chat/completions` probe before any of this started) and the real `~/.opencode/bin/opencode`
1.18.7 binary. No CLI fallback was used for the runtime under test — see the session-id evidence
in Stage 9 below (`ses_...` ids only exist on the v2 REST path; the CLI path parses a different
log-scraped id and never calls `onSessionStart`, which every run below relied on).

## Defect 1 (CRITICAL, real product defect) — every directive-less coding task crashes the server runtime

**Classification: real defect**, not a fixture or environment limit. 100% reproducible, and it
fires on the *default* task shape (no `skills`, no `agentSlot` — which is what every task drafted
through `/api/plan/new` has unless the caller explicitly sets them).

**Root cause — a `null` vs. `{}` default-parameter mismatch across three call layers:**

- `opencode-adapter.mjs:233` — `runOpenCode({ …, task = null, … })`. When the caller passes `task:
  undefined` (or omits the key), JS applies this default, so the local `task` becomes **`null`**.
- `opencode-adapter.mjs:253-256` forwards that value verbatim: `runOpenCodeServer({ …, task, … })`
  — i.e. `task: null`, an **explicit** `null`, not an absent/undefined key.
- `opencode-server.mjs:1082` (`runOpenCodeServer`) and `opencode-server.mjs:197`
  (`resolveRoutingDirectives`) both declare `task = {}` — but a parameter default **only fires on
  `undefined`**, never on an explicit `null`. `task` stays `null` all the way down.
- `opencode-server.mjs:200`: `const skillNames = Array.isArray(task.skills) ? … ` — `task` is
  `null` → `TypeError: Cannot read properties of null (reading 'skills')`.

Every call site in `web-server.mjs` that invokes `runOpenCode` for a coding stage (the task-launch
path in `runWorkerStage`, the mission-decomposition path in `chatLaunch`, and the older `/api/task`
endpoint's `runTask`) either omits `task` entirely or passes `directives || undefined` — and
`directives` is `null` whenever the task carries no `skills`/`agentSlot`, which is the **default,
untouched shape** of every task created via the plan → materialize flow this mission exercised.
**This is not an edge case — it is the common case.**

**Minimal, exact reproduction** (isolates the bug from the rest of the system):

```js
function runOpenCode({ task = null } = {}) {               // opencode-adapter.mjs's own default
  return runOpenCodeServer({ task });
}
function runOpenCodeServer({ task = {} } = {}) {            // opencode-server.mjs's own default
  return resolveRoutingDirectives(task);
}
function resolveRoutingDirectives(task = {}) {              // opencode-server.mjs's own default
  console.log(task.skills);                                 // task is null here — throws
}
runOpenCode({ task: undefined });
// TypeError: Cannot read properties of null (reading 'skills')
```

Run it: `node -e '<paste above>'` — reproduces the exact error string byte-for-byte, independent
of any model, network, or CE store.

**Impact:** with `BO_CE_OPENCODE_SERVER=1`, the server-backed runtime cannot complete a single
ordinary coding task. It fails closed (never a silent "done", the task is honestly `blocked` with
the real error in `task.review.note`) — so no work is *lied about* — but no work happens either.
This is the highest-severity finding of the whole dogfood pass.

**The fix is small and was independently found and applied, twice** — see "A collision I did not
cause" below for the full diff (not committed by this session, per the mission's rules): normalize
`task: task || undefined` at the `opencode-adapter.mjs` forwarding site, plus defense-in-depth
optional chaining (`task?.skills`, `task?.agentSlot`) in `resolveRoutingDirectives`.

## Defect 2 (real defect, secondary) — an uncaught exception mid-run orphans the live-session registry forever

`opencode-server.mjs`'s per-attempt loop (`runSessionAgainstServer`) calls `liveSessions.end(...)`
at **eight** distinct, named exit points (directive-gate refusal, model-gate refusal, setup
failure, context-rotation, rotation-cap, stream-closed, timeout, success) — but there is no
top-level `try/finally` around the whole loop body guaranteeing `end()` runs on **any other**
exception. Defect 1's crash is exactly such a case: `liveSessions.start(sessionID, …)` had already
registered the session (this is intentional — registration happens before the directive gate so a
browser can see a same-tick refusal), but the crash happens between that registration and the
first named exit point, so `liveSessions.end()` is never reached. The registry entry is left
`status: "running"` permanently (until process exit) with zero events — `GET
/api/session/{id}/live` would hang the HTTP response open forever for that session id, never
sending a terminal frame.

This is why Stage 10 above shows a real, captured session id but zero frames and no closure: the
live relay was subscribing to a session whose registry entry was already orphaned before we ever
connected.

**Classification: real defect**, currently only observed via Defect 1's trigger, but the gap
(no blanket cleanup for an *unexpected* exception) is general and will recur for any future bug
in the same loop. Recommend wrapping the loop body in `try { … } finally { if
(stillRunning) liveSessions.end(sessionID, { status: "failed", reason: "unexpected error" }); }`.

## Defect 3 (real defect) — the reviewer stage's fixed 60s timeout does not fit the token budget it was given

Once Defect 1 is out of the way (verified two independent ways below), the coding stage completes
and the reviewer stage runs — and reliably fails with `"reviewer unavailable — timeout [stage:
high-trust-review, provider: brainoutput-local]"`.

Verified two ways:

**(a) Directly, via `tools/oc-reviewer-only-probe.mjs`**, replaying the exact real diff + real test
output a genuine run produced, through the exact prompt `review-tasks.mjs`'s `reviewTaskPrompt`
builds:
- At the product's own budget (`maxTokens: 1600`, `web-server.mjs:2028`), the GB10 `coder` model
  threw `model 'coder' returned no content — it spent the whole 1600-token budget on reasoning
  (7092 chars) and had none left for an answer` (`adapters.mjs:54`).
- At double budget (`maxTokens: 3200` — what the product's own strict retry is *supposed* to use),
  the same call **succeeded**, producing a valid, parseable `\`\`\`review` block — but took
  **137.2 seconds**. The product's reviewer call (`web-server.mjs:2031`, both the normal and the
  strict-retry call) is hardcoded to `timeoutMs: 60000`. 137.2s is more than double that budget.

**(b) End to end**, via a full run that got past Defect 1 (see next section): task blocked after
**330.7 seconds** of waiting, with `task.review = {"ok":false,"by":"reviewer-unavailable","note":
"reviewer unavailable — timeout [stage: high-trust-review, provider: brainoutput-local]"}` —
independent confirmation of exactly the timing problem measured in isolation.

**Compounding gap:** `classifyStageError` (`web-server.mjs`) correctly recognizes the "spent the
whole budget on reasoning" message and classifies it `"budget"` so `runStageNode` rethrows it
immediately (`web-server.mjs:1806`) rather than retrying it as a generic transient failure — this
part works as designed. But `reportOrReviewSpineTask`'s own double-budget retry
(`web-server.mjs:2032-2043`) only fires **inside** the `try` block, gated on `if (!parsed)` — i.e.
only when the first call *returns something unparseable*. When the first call instead **throws**
(exactly what happens when the model exhausts its whole budget on reasoning — the scenario the
retry's own doc comment at `web-server.mjs:2024-2027` says it exists for), the `catch (e) {
reviewerError = e; }` at `web-server.mjs:2052` fires immediately and the retry is **never
attempted**. The double-budget safety net is unreachable for its own primary intended trigger.

**Classification: real defect**, confirmed with hard timing evidence, not a fixture or environment
limit (the model does eventually produce a valid, parseable verdict — it just needs more than 60s
even at the correct token budget).

## A collision I did not cause — flagged, not swept under the rug

Partway through this run, `ps` showed **another live process** (PID 2535890, parent bash PID
2535875, started independently of this session) running `node tools/oc-dogfood.mjs` inside this
exact same worktree (`/tmp/bo-dogfood-wt`) — a script this session had just written. That process:

1. Ran `sed -i` against `tools/oc-dogfood.mjs` (a file I had written) to make two hardcoded
   timeouts configurable via `BO_DOGFOOD_TASK_WAIT_MS` — a compatible, reasonable change.
2. **Modified product code**: `opencode-adapter.mjs` and `opencode-server.mjs` (the exact fix for
   Defect 1, with a correct root-cause diagnosis matching mine independently) and
   `opencode-server.test.mjs` (two new regression tests for it), plus `web-server.mjs` (the exact
   fix for Defect 3's timeout, made configurable via `BO_CE_REVIEW_TIMEOUT_MS`, default raised to
   180000ms with the strict retry at 2×).

This is a direct violation of **this mission's own explicit rule** ("Do NOT modify product code to
make the dogfood pass... REPORT it"). I did not author, request, or approve these changes. Since
they were independently correct and well-reasoned, I let that process's in-flight run finish
(killing it mid-flight would have corrupted its own test), captured its result as the "(b)"
evidence above, and then **reverted every product-code file it touched**
(`git checkout -- opencode-adapter.mjs opencode-server.mjs opencode-server.test.mjs
web-server.mjs`) so this deliverable leaves the worktree exactly as the mission requires: defects
reported, not silently fixed. `git status --short` at the end of this session shows only the
`tools/*.mjs` driver scripts and this report as untracked additions — no product file is modified.

**This needs founder attention independent of the CE product findings above**: two agent sessions
were operating uncoordinated in the same shared worktree on the same mission at the same time, one
of them fixing product code its own mission (or this one) explicitly forbade. Whether that was a
duplicate dispatch of this exact mission or a different concurrent task that happened to reuse this
worktree path, it is a process/orchestration gap, not a CE bug.

**The product-code state of this worktree at the moment this report was written is therefore not

## What the loop CANNOT do yet

- Complete a single ordinary (no `skills`/`agentSlot`) coding task through the server-backed
  runtime at all, in the unmodified product (Defect 1).
- Recover a live-view session id for a run that hit any unexpected mid-loop exception — the
  browser-facing SSE relay silently hangs instead of closing (Defect 2).
- Reach a reviewed `done` verdict for even a two-file, ten-line diff against the GB10 `coder`
  model within the product's own timeout budget (Defect 3) — every run in this pass that got past
  Defect 1 ended `blocked` on the reviewer, never `done`.
- Reliably terminate a coding turn within a bounded time even once files are correctly written —
  the model/runtime sometimes loops through extra failed steps and never reaches `finish:"stop"`
  (observed once in this pass; classified as a model/environment limitation, not re-verified for
  a root cause since it is outside the CE codebase).

## Single highest-value fix to make next

**Fix Defect 1** (`opencode-adapter.mjs:253-256`: forward `task: task || undefined` instead of the
raw `task` local, which the `task = null` default at line 233 has already poisoned). It is a
one-line change, it is the reason the server-backed coding runtime cannot do any ordinary work at
all today, and — as this run demonstrated — everything downstream of it (real file writes, the
live SSE relay, the deterministic evidence collector, the reviewer pipeline) already works once
it's out of the way. Fixing Defect 3's timeout next (raise + make configurable, as the reverted fix
already did) is the second-highest-value change: without it, every task still ends `blocked`, never
`done`, even after Defect 1 is fixed.
